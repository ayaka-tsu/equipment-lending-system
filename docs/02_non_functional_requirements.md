## 1. 本書の位置付け

本書は、機能以外の品質（性能・セキュリティ・運用保守など）に関する要件を定義する。
項目の分類は IPA「非機能要求グレード」の6大項目（可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、システム環境・エコロジー）に合わせた。
値は、このシステムの規模で**実際に検証できるもの**だけを定義し、要件ごとに検証方法を示す。

### ID の分類記号

| 記号 | 分類                     |
| ---- | ------------------------ |
| A    | 可用性                   |
| P    | 性能・拡張性             |
| M    | 運用・保守性             |
| T    | 移行性                   |
| S    | セキュリティ             |
| E    | システム環境・エコロジー |

## 2. 前提となる利用規模

| 項目                 | リリース時            | 5年後の想定  |
| -------------------- | --------------------- | ------------ |
| 利用者数             | 82名（うち管理者2名） | 150名        |
| 同時に操作する利用者 | 最大10名              | 最大20名     |
| 備品                 | 約450件               | 1,000件      |
| 貸出申請             | 年3,000件             | 累計15,000件 |
| 操作履歴             | 年13,000件            | 累計65,000件 |

性能の検証では、5年後の想定を上回る **備品1,000件・貸出申請20,000件・操作履歴70,000件** のデータを使う（NFR-P-01）。

## 3. 可用性

| ID       | 要件                                                                                                                                            | 検証方法                                           |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| NFR-A-01 | 主な利用時間は平日 9:00〜19:00 とする。時間外の利用も妨げない（24時間稼働）。                                                                   | －                                                 |
| NFR-A-02 | 独自の稼働率目標（SLA）は設けず、Vercel・Neon のサービス水準に準ずる。                                                                          | －                                                 |
| NFR-A-03 | DB のスキーマ変更を伴うリリースは、主な利用時間外に行う。                                                                                       | リリース手順書で確認                               |
| NFR-A-04 | システムが止まっている間の貸出は、総務部が紙の記録票で受け付ける。復旧後、社員本人がシステムで申請し、管理者がすぐに承認・貸出記録を行う。      | 運用手順として依頼元と合意                         |
| NFR-A-05 | 障害でデータが失われた場合に、24時間以内の時点へ戻せること（RPO 24時間）。1営業日以内に復旧すること（RTO 1営業日）。Neon のリストア機能を使う。 | リリース前にリストア手順を1回試す（未決事項 Q-03） |

## 4. 性能・拡張性

| ID       | 要件                                                                                                                                                          | 検証方法                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| NFR-P-01 | 性能検証用データ（備品1,000件・貸出申請20,000件・操作履歴70,000件）を入れた状態で、参照系 API（GET）は **500ms 以内**、更新系 API は **1秒以内** に応答する。 | ローカル環境で各 API を10回呼び、すべて基準内であることを確認する |
| NFR-P-02 | Neon がスリープから復帰した直後の最初のリクエストは、NFR-P-01・P-03 の対象外とする。                                                                          | －                                                                |
| NFR-P-03 | 画面を開いてから主要な内容が表示されるまで2秒以内（本番環境）。                                                                                               | 本番環境でブラウザの開発者ツールで計測                            |
| NFR-P-04 | 一覧の API は、DB 側でページングする（全件を取得してからアプリ側で絞らない）。                                                                                | コードレビュー                                                    |
| NFR-P-05 | 一覧の API で発行する SQL の回数が、表示件数に比例して増えないこと（N+1 問題を起こさない）。                                                                  | SQL ログを出して回数を確認                                        |
| NFR-P-06 | 利用者300名・備品3,000件までは、構成を変えずに対応できる設計とする。                                                                                          | 設計レビュー                                                      |

## 5. 運用・保守性

### 5.1 ログ・監視

| ID       | 要件                                                                                                                            | 検証方法                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| NFR-M-01 | 想定外のエラーは、スタックトレースを含めてサーバーログ（Vercel のログ）に出力する。利用者の画面にはスタックトレースを出さない。 | エラーを意図的に起こして確認 |
| NFR-M-02 | 業務操作を操作履歴に記録する（BR-14）。操作履歴は5年間保存し、削除・変更する機能は設けない。                                    | テスト                       |
| NFR-M-03 | ログにパスワード・セッショントークンを出力しない。                                                                              | コードレビュー               |

### 5.2 開発・リリース

| ID       | 要件                                                                                                      | 検証方法                  |
| -------- | --------------------------------------------------------------------------------------------------------- | ------------------------- |
| NFR-M-04 | `main` ブランチへ直接 push しない。Pull Request を作り、レビューで承認され、CI が成功してからマージする。 | GitHub のブランチ保護設定 |
| NFR-M-05 | Pull Request ごとに CI で lint・型チェック・テスト・ビルドを実行する。                                    | GitHub Actions            |
| NFR-M-06 | `main` にマージすると本番環境へ自動でデプロイされる。                                                     | Vercel の設定             |
| NFR-M-07 | 環境は「開発（ローカル）」と「本番」の2つとする。ステージング環境は設けない。                             | －                        |
| NFR-M-08 | DB のスキーマ変更はマイグレーションファイルで行う。本番 DB に手作業で DDL を実行しない。                  | コードレビュー            |
| NFR-M-09 | コーディング規約は ESLint・Prettier の設定に従う。開発ルールはリポジトリの `CONTRIBUTING.md` に従う。     | CI                        |

### 5.3 テスト

| ID       | 要件                                                                                                                                                         | 検証方法 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| NFR-M-10 | 業務ルールのうち、状態遷移（BR-07・08・16）、在庫の引当（BR-01〜04）、返却予定日の範囲（BR-05）、延滞・返却期限間近の判定（BR-06・15）には単体テストを書く。 | CI       |
| NFR-M-11 | 同時申請で在庫を超えて引き当てないこと（BR-02）を検証するテストを1件以上書く。                                                                               | CI       |

## 7. セキュリティ

### 7.1 認証・セッション

| ID       | 要件                                                                                                                                                                                                                | 検証方法                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| NFR-S-01 | ログイン API を除く全画面・全 API で、ログインを必須にする。                                                                                                                                                        | テスト                                   |
| NFR-S-02 | パスワードは bcrypt（コスト10以上）などの、パスワード保存用のハッシュ関数で保存する。平文、復号できる暗号化、MD5・SHA-256 の単体使用は禁止する。                                                                    | コードレビュー                           |
| NFR-S-03 | セッショントークンは暗号論的に安全な乱数で32バイト以上とする。Cookie には `HttpOnly`・`SameSite=Lax`・`Path=/` を付け、本番では `Secure` も付ける。DB にはトークンそのものではなく SHA-256 のハッシュ値を保存する。 | コードレビュー、ブラウザで Cookie を確認 |
| NFR-S-04 | セッションの有効期限はログインから8時間とする。ログアウトしたらセッションを DB から削除する。                                                                                                                       | テスト                                   |
| NFR-S-05 | ログインに失敗したとき、メールアドレスとパスワードのどちらが誤っているかを区別しない（BR-17）。                                                                                                                     | テスト                                   |

### 7.2 認可

| ID       | 要件                                                                                                              | 検証方法                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| NFR-S-06 | 権限のチェックは必ずサーバー側（API と画面の両方）で行う。ボタンを隠すことは権限のチェックとみなさない。          | テスト（一般社員の Cookie で管理者 API を呼び、403 になることを確認） |
| NFR-S-07 | 他人の申請を一般社員が取得しようとした場合は、403 ではなく **404** を返す（申請が存在すること自体を知らせない）。 | テスト                                                                |

### 7.3 入力・出力

| ID       | 要件                                                                                                                                        | 検証方法             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| NFR-S-08 | すべての API で、サーバー側で入力を検証する。画面側の検証だけに頼らない。                                                                   | テスト               |
| NFR-S-09 | SQL はプレースホルダ（パラメータバインド）で組み立てる。利用者の入力を文字列連結で SQL に埋め込まない。                                     | コードレビュー       |
| NFR-S-10 | `dangerouslySetInnerHTML` を使わない。                                                                                                      | lint・コードレビュー |
| NFR-S-11 | 更新系 API（POST・PATCH・DELETE）は、`Origin` ヘッダが自サイトと一致しない場合に 403 を返す（CSRF 対策。Cookie の `SameSite=Lax` と併用）。 | テスト               |
| NFR-S-12 | エラー応答にスタックトレース・SQL・内部のファイルパスを含めない。                                                                           | テスト               |

### 7.4 秘密情報・その他

| ID       | 要件                                                                                                                                                  | 検証方法             |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| NFR-S-13 | 次の対策は第2期で検討し、本プロジェクトでは実装しない：アカウントロック、パスワードリセット、多要素認証。利用を社内に限定することでリスクを受容する。 | －                   |
| NFR-S-14 | DB の接続文字列などの秘密情報は環境変数で渡す。`.env` をコミットしない。必要な変数は `.env.example` に値なしで列挙する。                              | コードレビュー       |
| NFR-S-15 | 保存する個人情報は、社員の氏名・社員番号・メールアドレス・部署に限る。                                                                                | テーブル定義レビュー |
| NFR-S-16 | 通信はすべて HTTPS とする（Vercel の標準機能）。                                                                                                      | －                   |

## 8. システム環境・エコロジー

### 8.1 利用環境

| ID       | 要件                                                                                                                | 検証方法                     |
| -------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| NFR-E-01 | 対応ブラウザは Google Chrome と Microsoft Edge の最新版とする（依頼元の社内標準）。                                 | 受入テスト                   |
| NFR-E-02 | 画面幅1280px 以上で最適に表示する。幅375px でも、横スクロールなしで閲覧と貸出申請ができること（最適化は求めない）。 | ブラウザの開発者ツールで確認 |
| NFR-E-03 | フォームの入力欄にはラベルを付ける。主要な操作はキーボードだけでもできる。状態は色だけでなく文字でも表す。          | 受入テスト                   |

### 8.2 時刻・文字

| ID       | 要件                                                                                                                                                     | 検証方法                                                     |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| NFR-E-04 | 日時は DB に `timestamptz` で保存する。画面の表示と日付の判定は日本時間（Asia/Tokyo）で行う（BR-18）。サーバーのタイムゾーン設定に依存しない実装にする。 | テスト（環境変数 `TZ=UTC` で実行しても結果が変わらないこと） |
| NFR-E-05 | 文字コードは UTF-8 とする。                                                                                                                              | －                                                           |
